## 4. Device-testing preparation (built in M2.2)
A phone has no command line, so measurement is built into the app.

**Opening the tools:**
- Hold the **Đồ họa** button for about 1 s and release; the device panel opens. A short press still cycles the preset.
- The panel shows build version, commit, debug/release, model, OS, GPU, load time, and whether the previous run ended abnormally.

**Panel functions:**
- **HIỆN SỐ ĐO** shows a live overlay:
  - preset, FPS, draw calls;
  - p50/p95/p99 frame time, % of frames over 33 ms, max;
  - RAM (debug builds) and VRAM.
  - It sits beside the action panel, not over the board.
- **ĐO TỰ ĐỘNG** plays the match via the HUD autopilot and records Thấp / Vừa / Cao for 60 s each (1.5 s warm-up ignored), then restores the player's preset.
- **LƯU BÁO CÁO** writes the report now. It is also saved every 30 s and when the app goes to the background.

**Report** `user://device_validation/run_<unix>.json`, reachable in the iOS Files app:
- build stamp (commit and time, from `scripts/export_build.sh`);
- device fields: model, OS, GPU, API, screen, safe area, refresh rate, orientation;
- load times;
- one frame-time segment per preset;
- input latency: touch dispatch → next submitted frame;
- memory peaks;
- previous-session state.

Telemetry (`user://telemetry/`) and the engine log (`user://logs/`, now enabled on mobile too) sit next to it.

**What these numbers are and are not** (also documented in the code):
- Frame time is the engine frame delta.
- Input latency excludes the touch digitizer and display scan-out. The checklist adds a 240 fps camera method for end-to-end latency.
- Godot tracks static memory only in debug builds, so release reports show `null`. The iOS footprint must come from Xcode.

**How to measure FPS / frame time on the iPhone** (`IOS_BUILD_GUIDE.md` §5, checklist §E):
1. Release build.
2. In-app benchmark 3 × 60 s in portrait and landscape, fresh, after 15 min and after 30 min.
3. Cross-check one run with Instruments (Metal System Trace / Game Performance) or the Metal Performance HUD.
4. Record memory footprint and thermal state from Xcode.
5. The proposed pass bar is in the checklist: Thấp/Vừa p95 ≤ 33.3 ms and ≤ 5% of frames over 33 ms. This is a proposal for the owner.

**Every real result must carry:** device + model number, iOS, build commit, debug/release, preset, orientation, battery / charger / Low Power Mode, room temperature (header of `IPHONE14PRO_TEST_CHECKLIST.md`).

## 7. Fix or decide before starting M3
1. **Offline clock counts background time** (found by code reading; to confirm on device, checklist D5/D6).
   - `LocalMatch` advances the rules clock by the frame delta. When iOS suspends the app, the first frame after resume carries the whole suspension.
   - So a 5-minute background can expire the 45 s turn timer (safe default applied) and counts towards the 30-minute cap.
   - **Decision needed:** offline should pause the match clock. Online (M3) keeps server timers running and needs reconnect plus snapshot.
   - This is presentation/offline-host code, not a rule change, but it changes timer semantics, so it is listed rather than changed silently.
2. **No real-device numbers yet.** The GDD §14 mobile criteria (30 FPS low/medium on the baseline device, readable labels, safe areas) cannot be signed off. The device checklist should run in parallel with the M3 spike, before M4.
3. **Signing inputs from the owner:** Team ID, bundle ID, Mac access.
4. **No CI.** `scripts/run_tests.sh` only runs by hand (open risk in IMPLEMENTATION_PLAN §5). Add a headless CI job before M3 adds network tests.
5. Minor:
   - The device panel is reachable in release builds; gate it (feature tag or settings) before any public release.
   - Two app instances started in the same second share one report filename (desktop only).
   - No audio exists yet (M4 scope).
   - `boot_splash/fullsize` export warning (harmless).
